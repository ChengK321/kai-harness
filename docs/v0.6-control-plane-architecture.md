# Kai Control Plane V0.6 Architecture

## 1. Purpose

**Kai = Agent Control Plane**，而不是 **Kai = Agent Framework**。
Kai 当前定位不是替代 Claude Code、Codex 或其他 Agent Runtime，而是通过薄控制层
管理外部 Agent 的执行边界。

Kai 的职责包括：

- Agent 生命周期管理：启动、执行预算、超时和结果处理。
- Workspace 隔离：限定工作目录与执行环境边界。
- 权限边界控制：限制可用工具和环境权限。
- 执行策略管理：明确运行参数和允许的执行方式。
- 审计：使执行过程与结果可追溯。
- Environment 管理：区分项目、测试和未来部署或机器人环境。

这些是 Control Plane 的职责范围，不表示全部能力已经实现。当前代码提供最小
Harness Runner，尚未提供完整生命周期服务、持久化审计或系统级环境隔离。
Kai 不实现 LLM reasoning、Agent loop、Planner、Memory backend 或 Model Provider。

## 2. Evolution from V0.5

V0.5 的设计演进：

```text
Infrastructure
  ↓
Core Contract
  ↓
Registry
  ↓
Validator
  ↓
Runtime Design
```

V0.6 的架构方向：

```text
Control Plane
  ↓
Agent Harness Adapter
  ↓
External Agent Runtime
  ↓
Workspace
  ↓
Environment
```

V0.5 的 Runtime、Memory、Policy 设计没有废弃；它们保留为未来机器人 Agent Runtime、
Memory System 和 Safety Layer 的设计参考，不表示已启用，也不承诺原样实现。
当前实现不主动重复 Claude Code 已经提供的能力。

历史契约保留原义，历史文件保留原位。V0.5 的自研 Runtime 路线不再代表当前实现方向；
相关 Runtime 和 Memory 设计属于 **Future Design / Not Active Runtime**。
Current Kai does not implement persistent Agent Memory.

## 3. Current Implementation Architecture

当前请求到结果的概览：

```text
User Request
  ↓
kai-agent CLI
  ↓
runner.py
  ↓
Claude Code CLI
  ↓
Model Provider (DeepSeek / Claude / Other)
  ↓
Workspace
  ↓
JSON Result
  ↓
User
```

此图表示请求涉及的环节。实际由 Claude Code 调用模型、解释模型响应并在 workspace
使用工具，模型 Provider 不直接访问本地文件。JSON 由 Claude Code 输出，经过 Runner
解析和 CLI 格式化后返回用户。当前 Provider 为 DeepSeek；其他 Provider 取决于外部
Harness 的支持与启动环境配置，Kai 没有实现 Provider 切换框架。

| 模块 | 当前职责 |
| --- | --- |
| User Request | 提供 prompt 和 workspace 路径。 |
| kai-agent CLI | 使用 argparse 接收参数，调用 Runner，显示结果并返回退出码。 |
| runner.py | 校验路径，构造参数数组，以 workspace 为 cwd 执行 Claude，捕获和解析输出。 |
| Claude Code CLI | 承担 Agent loop、模型交互和获准工具调用，输出 JSON。 |
| Model Provider | 为 Harness 提供模型推理服务。 |
| Workspace | 承载本次任务可操作的项目材料。 |
| JSON Result | 经 Runner 转为 HarnessResult，再由 CLI 向用户展示。 |

当前命令固定启用 `--bare`、`--strict-mcp-config`、`Read,Glob,Grep`、最大 5 轮、
JSON 输出和 `--no-session-persistence`。Runner 使用 `shell=False`，默认超时 300 秒。
进程继承启动环境；Runner 不读取 API Key 文件，也不负责注入模型凭据。

## 4. Current Components

### kai-agent

位置：`apps/kai-agent`。

职责：

- 调用 Claude Code。
- 管理并校验 workspace 参数。
- 限制工具参数。
- 解析 JSON 输出。
- 返回 HarnessResult，包含状态、退出码、结果、会话、轮数、耗时、费用、权限拒绝和 stderr。

它不是 Agent Brain、Planner 或 Memory Manager。
启动失败、非零退出、超时和无效 JSON 通过明确异常交给 CLI 展示。

### Claude Code

Claude Code 是当前 Agent Runtime，负责 reasoning（通过模型交互）、tool usage、
code modification 和 verification 等 Agent 能力。Kai 不重新实现这些能力。

上述为 Harness 的能力范围；当前 Kai 只开放 `Read,Glob,Grep`，不开放 `Edit`、
`Write` 或 `Bash`，因此当前 Runner 不授权代码修改或命令式测试执行。

### Workspace

Workspace 是 Agent 默认执行边界，包含项目代码、项目配置和测试环境材料。
当前根路径是 `/srv/kai/workspaces/`，目录布局见 [workspace-layout.md](workspace-layout.md)。

边界要求：

- Agent 不访问任意系统目录。
- Agent 不访问 secret。
- Agent 不直接管理系统服务。

当前 Runner 要求 workspace 为绝对路径、实际存在且是目录，解析符号链接后严格位于
根路径之下；根目录本身和符号链接逃逸均拒绝。路径校验和 cwd 只限制启动目录，
不是文件访问沙箱；上述访问要求还需要部署环境的权限控制落实。
项目配置不得包含供 Agent 读取的 secret；运行凭据由受控启动环境管理。

## 5. Security Boundary

目标部署边界如下，此图不是当前 Runner 已执行用户切换的声明：

```text
ubuntu user
  |
  | 受控启动
  v
kaiagent
  |
  | 限定工作目录和权限
  v
workspace
  |
  | cwd
  v
Claude Code
```

`kaiagent` 作为目标执行身份，允许获授权的 workspace 操作；当前工具策略仅允许只读操作。
禁止权限包括：

- sudo
- docker
- system config
- secret access

当前 Python Runner 继承调用进程的用户身份，不创建 `kaiagent`、不切换用户、
不设置系统权限，也不证明上述部署限制已经生效。操作系统级边界由部署层负责。
本架构文档不执行任何账户、Docker、Nginx、Xray、SSH、防火墙或系统服务变更。

## 6. Future Extension

### Website Agent

```text
User
  ↓
Web UI
  ↓
Kai Control Plane
  ↓
Agent
  ↓
Modify Code
  ↓
Test
  ↓
Deploy
```

此流程是未来扩展方向，当前只读 Runner 不提供修改、测试命令或部署能力。
未来需由执行策略明确授权，并由独立 Environment 承担部署权限。

### Robot Agent

```text
Robot Observation
  ↓
Agent
  ↓
Planner
  ↓
Safety Layer
  ↓
ROS2 Environment
  ↓
Robot Action
```

Planner 属于外部机器人 Agent Runtime，Safety Layer 约束机器人动作；
它们不是在 Kai Control Plane 内重建 Agent loop 的理由。
V0.5 设计可作为这些组件的输入。

未来扩展通过 Adapter 接入，不修改 Control Plane 的职责与核心架构，
不将网站或机器人专属推理、规划和执行逻辑放入控制面。

## 7. Repository Layout

| 目录 | 用途 |
| --- | --- |
| `apps/` | 应用代码；当前 Harness 代码位于 `apps/kai-agent`，Registry Validator 保持独立。 |
| `configs/` | 配置声明、Registry 和 Schema；历史设计配置不等于已启用的运行配置。 |
| `docs/` | 当前架构说明、ADR 和保留的历史设计。 |
| `data/` | 数据目录约定；存在目录不代表已有持久化 Agent Memory。 |
| `runtime/` | 运行材料的目录约定；目录名不代表 Kai 已实现 Agent Runtime。 |
| `versions/` | 版本记录与版本材料的目录约定。 |
| `backup/` | 备份材料的目录约定。 |

历史资产包括 [runtime-design.md](runtime-design.md)、[memory-design.md](memory-design.md)
及 [Registry 设计](registry-design.md)、`configs/registry/` 中的声明。
Registry 和 Validator 仍属于控制面职责；历史文档中的 Runtime 集成链路
不表示当前 Runner 已加载 Registry 或绑定 Snapshot。

## 8. Architecture Decision Records

以下汇总当前架构决策；ADR-001 对应已有 ADR-0001，ADR-002 和 ADR-003 在本文记录，
本次不创建独立 ADR 文件。

### ADR-001: 采用 External Agent Harness

Kai 不实现基础 Agent Runtime，采用 External Agent Harness。
当前选择 Claude Code，遵循已有
[ADR-0001](decisions/ADR-0001-kai-harness-boundary.md)。

### ADR-002: Control Plane 与 Execution Environment 分离

Control Plane 管理启动、策略、边界和结果；Execution Environment 承载实际操作
及环境权限。控制面职责不包含直接管理 Agent 任务所涉及的系统服务。

### ADR-003: Workspace 是 Agent 默认执行边界

Agent 默认在明确授权的 workspace 执行。当前通过路径校验、cwd 和工具限制实施
最小约束，完整访问隔离由执行环境落实；不把路径校验等同于操作系统级沙箱。
